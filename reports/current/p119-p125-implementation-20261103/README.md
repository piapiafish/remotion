## 原始现象、原因与实际边界

修复前使用个人工程副本进行了两轮基线诊断。连续拖动对象行空白从 30% 到 80% 时，播放头仍停在 2.4 秒；编辑最低设备的缩放使公共地面从约 -1.501 降到 -2.683；未保存流程为原生确定/取消。见 [校正后的基线](baseline-corrected/report.json)。第一轮探针选了非最低设备和不存在的模板 ID，未能正确覆盖这两项；原记录保留，不把探针不足解释成产品通过。

个人录屏为 720×1584、约 18.084 秒、H.264，标称 120FPS、平均约 103FPS；元数据见本目录 `private/user-recording-ffprobe.json`。自然单视频基线未出现源帧倒退，不能仅凭用户描述断言已定位所有卡顿根因。新版双视频约 12 秒中分别呈现 1059、238 个解码帧，两个实例没有倒退、播放中重新定位次数均为 0。解码帧数量不是画布显示帧率或性能保证，记录见 [播放数据](fixes-final/playback.json)。

另外在没有三维场景干扰的实际视频解码器上，注入 +0.25 秒偏差并暂停调度 200ms，对照原 0.12 秒硬校正逻辑和新版软校正。旧逻辑出现 1 次向后定位和 1 次倒退画面，新方式均为 0。它证明该类偏差导致的重播路径得到处理，不代表已自然复现用户所有大幅变化画面的卡顿。实际机器的流畅度及默认大小可读性仍需复核。

默认预览提升是受控超采样；源像素不足、设备在画面中很小仍有限制。320 万像素为采样预算目标，最低保持 1 倍 CSS 分辨率，CSS 画布本身更大时可能超过该目标。没有对 4K、60FPS、大量设备或 120FPS 实时播放作保证。

播放中的效果预览使用两次姿态采样和当前连续视频帧；暂停与导出才精确取各曝光时刻的录屏，播放拖影细节可能不同。两者的姿态时间、素材时序、固定地面和最终导出链路共用。字体仍使用本机字体。

文件选择器成功路径在自动化中返回真实 OPFS 可写句柄，验证写入、关闭与继续的顺序；系统原生“保存位置”窗口本身尚未人工操作验收。取消和磁盘失败使用受控注入，下载回退实际取得 `.mockup` 后，明确确认才继续。

五机型检查覆盖实际混合旋转、缩放和旧朝向的网格底部；不代替逐机型四面、材质、贴屏及最终视觉验收。60 秒未在本轮重复，历史证据仍属于此前轮次。用户未填的其他场景、新模型、在线 AI、自动草稿和完整多镜头/音乐轨道按原计划保留。

## 保留的诊断失败

- `tests-first` 三项失败来自新 groundY 迁移字段与自定义提示的旧断言；更新为验证兼容默认值及新的继续动作，保留原素材、轨道和取消保护断言。`tests-second` 一个几何比较差约 7.9e-8，依据 Float32 顶点精度采用 1e-6 的比较容差。最终 355 项通过。
- `fixes-01` 的保存按钮选择器因“不保存”包含相同字串而匹配两项；改为精确匹配。该轮导出期间开发文件变动触发 Vite page reload，下载等待超时；源变动与原失败日志保留。
- `fixes-02` 实际产生 4 秒/120 帧视频，但模板为 4:3，输出 1600×1200；它不满足 1080P 测试要求。`fixes-final` 明确选择 16:9 后实际输出 1920×1080，通过完整 32 项。
- 最初 `models-final` 的双机比较构图为竖屏，投影区域证明不足；视觉检查后改为完整横向构图，并要求采样区确实含有阴影像素，以 `models-verified` 作为最终证据。旧报告保持原样。
- 首次文档检查时本报告已引用尚未生成的 `document-check.json`，产生一条本地链接错误；生成该证据后重跑实际链接检查通过，初始输出另存。旧根目录的文档检查文件在两轮后均恢复原字节。
