# Composition Engine｜多设备智能构图引擎技术方案

## 目标不是禁止设备出画，而是让大模型掌握“最终画面中的空间关系”

让普通多模态能力的大模型生成高层构图：设备组合在画面的哪里、占多大比例、有哪些文字、谁是主角、入场/展开/停留/退场如何运动。确定性布局引擎负责把目标转成能在原 Three.js 场景运行的坐标和关键帧。

**保留自由度**：世界坐标、角度、深度和时长仍可连续变化；模板只是初稿；用户可有意放大到超出画面、从不同方向进出、让多个设备相互遮挡。

## 1. 坐标与层级

- **屏幕空间**：`u,v∈[0,1]` 是视频目标画面中的归一化坐标（仅表示可见画面范围）；画外可用 `u<0 / u>1` 等表达，不强制截断。
- **世界空间**：原 Three.js 实际坐标，受相机位置、FOV、宽高比、设备 modelTransform 影响。
- **组空间**：`M_i(t) = M_group(t) × M_local_i(t) × M_assetFix_i`，注意实现中原 modelTransform 可能已在内部应用，要确保**只修正一次**。
- **文本空间**：标题、字幕等留白区域位于屏幕空间，不强制写死世界位置。

推荐抽象：

```ts
// 仅为协议建议，不代表已实现
interface VisualIntent {
  canvas: { width: number; height: number };
  composition: {
    anchor: [number, number];       // 组目标视觉中心，可在 [0,1] 外
    targetWidth?: number;          // 占据画幅宽度比例
    targetHeight?: number;
    textRegion?: 'left'|'right'|'top'|'bottom'|'none';
    alignment?: 'center'|'bottom'|'top';
    spacing?: number;              // 可连续调节的间距目标
    allowOffscreen?: boolean;
    allowOverlap?: boolean;
  };
  devices: Array<{
    deviceId: string;
    relativeScale?: number;
    role?: 'primary'|'secondary';
    localPose?: { position?: [number,number,number]; rotation?: [number,number,number] };
  }>;
  phases: Array<{
    time: number; phase: 'entrance'|'transition'|'hero'|'exit';
    groupAnchor?: [number,number];
    groupScale?: number;
    localAdjustments?: Record<string, unknown>;
  }>;
}
```

**绝不直接将字段解释成固定 Three.js 坐标表。** 语义字段应由布局引擎求解，并生成原工程可编辑的 TrackSet。

## 2. 真实包围盒投影与设备尺寸

1. GLB 加载完成且 `matrixWorld` 已更新之后，为每台设备取得世界坐标下包围信息（或导入并应用离线测量元数据）；确认修正矩阵与节点层级一致。
2. 对可见几何的包围盒顶点/代表性轮廓点调用 `Vector3.project(camera)` 投影至 NDC，再转换为 normalized screen coordinates。
3. 以有效投影点算最小投影矩形 `(minU,minV,maxU,maxV)`、画面中心、可见占比和组区域。近裁切面穿过包围盒时需要裁剪或使用合适的保守估计；相机背后的点不能直接参与矩形计算。
4. 面向功能演示时，除机身包围框外，还要单独投影**屏幕可见区域**，评估录屏是否足够大和可读。
5. 不能只看设备中心点：一个中心在画面中的巨大模型，仍可能占满甚至挡住所有文字。

边界说明：投影包围盒是保守几何估计，不等于像素级可见轮廓；复杂透视、遮挡和宽 FOV 需要通过实际渲染预览确认。

## 3. 单设备构图求解（MVP）

给定 `anchor`, `targetWidth/Height`, `screenReadableArea`，先选默认相机和旋转；通过实测投影结果迭代调整**组的位置/深度/缩放及可选相机**，使下列目标接近预期：

- 目标中心偏差 `E_center`
- 尺寸偏差 `E_size`
- 与文字区域非故意重叠 `E_text`
- 设备屏幕可读面积不足 `E_readability`（主要在核心展示阶段）

不要把所有误差都设为必须为 0：左重右轻的非对称构图是合法的；根据用户是否允许重叠、是否故意出画调整各项权重。布局只在关键阶段求解，之后依赖已存在的插值系统。

## 4. 多设备构图（优先组运动）

需要两层动作：

- **组变换**：所有手机共同入场、移动、缩放、退出，保证组整体视觉中心和占比一致。
- **设备局部变换**：每台手机独立旋转、偏移、错层、相对缩放；组内可展开、交叉、层叠，不禁止创意。

默认布局种子（均可连续调参数）：

- 两手机紧凑并列 + 右侧文案。
- 三手机中央突出，两侧后移或旋转。
- 五手机从屏幕外逐步扇形展开。
- 不同屏幕尺寸手机/平板混合，以投影实际尺寸而非模型单位决定视觉比例。

求解目标应优先保持**设备组包围区域**合理，而不是分别让每台手机居中。设备错层造成的有意重叠要允许；若用户要求清楚展示每台屏幕，才把屏幕遮挡当作软性惩罚。

## 5. 运动阶段与采样

镜头可描述：`entrance → spread/transition → hero/hold → exit`。

- `entrance`：允许从可见画面外出发；不因为投影矩形越界而自动修复。
- `transition/spread`：允许不同设备错时和独立运动；对组合结构散开程度做柔性评估。
- `hero/hold`：一般保障视觉中心、设备主要屏幕清晰、留白适当；特殊风格可覆盖。
- `exit`：允许全部或部分设备离开画面。

根据绝对时间编排 `sampleTimeline(project,t)`；对关键帧边界和必要的中间时刻抽样，检查跳变、间距、屏幕占比。自动改动优先作用于**关键阶段目标参数**，不要在每帧施加独立的强制纠偏导致抖动。

## 6. 调整策略与用户体验

当目标画面存在明显缺陷，按以下成本低到高处理：

1. 轻微调整设备组 `anchor` / `scale`。
2. 调整设备局部间距与相对深度。
3. 调整相机 FOV/距离（仅在与镜头意图兼容时）。
4. 提供一张包含投影框/文字安全区的低分辨率预览，让 LLM 或用户选择是否接受。

用户的明确指令优先于默认构图策略。模型位置可以画外，只需**在要求展示功能的阶段**保证可读性。所有自动建议应可撤销。

## 7. 与现有代码的集成边界

阅读：`src/devices/manifest.ts`、`src/scene/GltfDevice.tsx`、`src/timeline/sample.ts`、`src/timeline/templates.ts`、`src/timeline/presets.ts`。

建议新增（需按实际项目做路径决策）：

```text
src/composition/
├── types.ts               # 画面意图及阶段数据
├── projection.ts          # GLB / 组投影包围框
├── groupLayout.ts         # 多设备组布局与局部变换
├── solveLayout.ts         # 单/多设备构图求解
├── compileTracks.ts       # 输出原 TrackSet
└── __tests__/             # 不同机型/长宽比/进出场
```

**不要另建一套 3D 渲染器，也不要由 LLM 在运行时生成 Three.js 源码。** 先提供纯函数与可调试的预览数据，再与现有 R3F 页面接通。

## 8. 验收用例

| 场景 | 期望 |
|---|---|
| 单机左侧，右侧文案，横屏 16:9 | 投影大小和目标锚点合理，文字区无非预期遮挡 |
| 单机画外入场 | 起始合法画外，展示阶段进入画面，退场可离开 |
| 双机同时平移 | 间距保持视觉协调，不会随机发散 |
| 三机中心聚焦 | 中间突出，左右错层，允许有意遮挡 |
| 五机展开 | 可从画外分步进入后排列，不强制固定位置 |
| 手机+平板混合 | 依据可见投影尺寸缩放，不按世界单位机械相等 |
| 由 16:9 切换 9:16 | 求解结果自动适配画幅而非直接复制固定坐标 |
| 用户修改一个旋转关键帧 | 不重建其余轨迹，仍能撤销 |
