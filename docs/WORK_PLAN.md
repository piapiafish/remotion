# Multi-Agent 3D 产品宣传片生成系统

**基于 Device Mockup Studio 源码的审查报告与分阶段工作规划**

*项目工程规划 · 2026-10-08*

| **规划定位** | **具体说明**                                                                 |
|--------------|------------------------------------------------------------------------------|
| 输入基础     | 用户上传的 device-mockup-studio-main.zip（本地源码 + 4 个 GLB 模型）         |
| 产品定位     | 从源码/录屏/文字说明出发，由 AI 规划并生成软件产品宣传视频                   |
| 推荐路线     | 保留现有 3D 可视化核心 → 建立无头渲染适配 → 视频 DSL → Agent → Remotion 合成 |
| 第一里程碑   | 可生成并交付 15–30 秒、含真实设备镜头、字幕和配乐的 MP4                      |
| 规划性质     | 面向可执行研发的工作规划，不等同于已完成的系统联调或性能保证                 |

## 核心技术决策

先复用已实现的 Three.js / React Three Fiber 设备镜头能力，避免一开始把整个编辑器重写成 Remotion。先让 Agent 通过稳定的工具接口驱动单镜头渲染，再由 Remotion 拼接完整影片。

特别说明：本次已直接解包并检查上传的源码、核对四个 GLB 文件结构与 SHA-256；未成功执行 npm ci、浏览器启动及视频渲染，相关能力以源码存在为依据，后续必须通过 P0 验证。

# 01｜决策摘要：我们究竟要做什么

## 1.1 产品目标

让用户提供 APP 录屏、软件截图和一句产品介绍，即可自动产出具有真实 3D 手机展示、镜头运动、动态字幕、旁白和音乐的宣传片。后续再升级为读取软件项目源码、识别功能并半自动或自动录屏。

## 1.2 MVP 明确做 / 暂不做

| **首版必须完成（MVP）**                                | **后续再做（V2/V3）**                              |
|--------------------------------------------------------|----------------------------------------------------|
| 用户上传录屏/截图/产品说明；选择设备与风格             | 自动启动任意用户项目并完成跨平台操作录屏           |
| AI 生成结构化分镜并可人工修改                          | 完全无人干预、跨多框架的软件视觉理解               |
| 调用本地 GLB、视频贴图、镜头预设，输出可复查的镜头片段 | 自研 3D 建模器 / 自研视频编码器 / 任意格式自动修复 |
| Remotion 合成字幕、音乐、镜头切换，得到 MP4            | 电影级粒子/景深/复杂角色动画                       |
| 失败回退、基本质量检测、导出日志                       | 无限制多 Agent 层级与全自动审美评估                |

## 1.3 两条基本原则

- 确定性底座 + 自由创作上层：AI 决定分镜表达，程序保证时间轴、资产路径、设备屏幕映射及可重复渲染。

- 以视频成片为验收，不以 Agent 数量或流程复杂度为验收；每完成一阶段，都能独立演示。

## 1.4 推荐架构（第一版）


```text
用户素材 / Brief
↓
Planner / Director Agent → Storyboard JSON（Video DSL）
↓ 校验 + 编译
DeviceShot 工具适配层 → 既有 Three.js / R3F / GLB 引擎
↓ 逐镜头视频 / PNG 序列
Remotion 合成层 → 标题 / 旁白 / BGM / 转场 / 品牌尾版
↓
Critic / 规则检查 → 最终 MP4 + 过程日志
```


重要：原仓库本身不是 Remotion 工程；它当前的导出方式是浏览器 WebCodecs（MP4/WebM）或 PNG 序列。第一版推荐「已有渲染引擎负责设备镜头、Remotion 负责整片合成」的松耦合模式。

# 02｜上传源码的审查结论

## 2.1 本地实物验证

从上传的 ZIP 提取 133 个归档条目；源码位于 device-mockup-studio-main/，内含真实设备模型。四个 GLB 均通过二进制文件头（glTF v2）、文件声明长度一致性检查，并且 SHA-256 与其 ASSETS.md 内的公开清单一致。

| **模型文件**          | **大小** | **核对结果**         |
|-----------------------|----------|----------------------|
| iphone-17-pro.glb     | 5.11 MB  | GLB v2；SHA-256 匹配 |
| iphone-17-pro-max.glb | 15.31 MB | GLB v2；SHA-256 匹配 |
| galaxy-s26-ultra.glb  | 2.29 MB  | GLB v2；SHA-256 匹配 |
| pixel-9-pro-xl.glb    | 9.90 MB  | GLB v2；SHA-256 匹配 |

这是「容器文件合法与来源清单一致」的验证，并不代表已逐台完成纹理视觉、视频贴图方向、动画与离线渲染功能的运行验证。

## 2.2 已有能力与源文件对照

| **现有模块（源码证据）**                           | **能直接做什么**                                      | **复用策略**             |
|----------------------------------------------------|-------------------------------------------------------|--------------------------|
| src/devices/manifest.ts                            | 注册设备 ID、GLB 路径、屏幕材质、尺寸、颜色、修正变换 | 保留并规范扩展           |
| src/scene/GltfDevice.tsx、materials/\*             | 将图片/视频纹理映射到真实屏幕 Mesh，处理 UV/比例      | 保留，补自动验收         |
| src/media/screenVideo.ts                           | 录屏时钟同步、逐帧 seek                               | 保留，重点做离线渲染回归 |
| src/timeline/sample.ts、presets.ts、templates.ts   | 固定时间 t → 镜头状态；动作、镜头、多机模板           | 直接复用数据与算法       |
| src/export/frameRenderer.ts、video.ts、sequence.ts | 超采样、逐帧捕获、WebCodecs 或 PNG 序列导出           | 封装成无头任务           |
| src/store/schema.ts、project.ts、persist.ts        | 工程数据、编辑/撤销、工程打包与恢复                   | 沿用，外层加独立 DSL     |
| src/ui/\*、src/App.tsx                             | 可交互编辑器及预览                                    | 保留为人工兜底界面       |

## 2.3 现阶段不具备的能力

- 没有产品级 Agent 编排、自然语言到稳定的镜头任务编译、服务端任务队列与产物管理。

- 没有开箱即用的 Remotion 全片合成工程；需要新建集成层。

- 没有现成的跨框架源码理解与自动录屏流程；只把它列为 V2。

- 仓库内只有 4 台真实 GLB 手机，不包含已可直接用于生产的 MacBook、iPad、Watch 资产。

- 已有 20 个 \*.test.ts 测试文件，但在本次环境中未安装依赖、未执行测试/构建与 GPU 渲染，因此测试结果不可提前认定为通过。

# 03｜保留、改造、新增：代码级复用边界

| **处理方式** | **范围 / 对应源码**                                                                | **决策理由**                                     |
|--------------|------------------------------------------------------------------------------------|--------------------------------------------------|
| 保持原样优先 | src/scene、src/devices、src/timeline、src/media；public/devices                    | 底层已解决建模/UV/时间轴核心问题；减少回归风险   |
| 薄适配       | src/export/\* 与 src/store/\* 外层新建 automation / render bridge                  | 把依赖 UI 操作的流程变成可重复、可观测的任务接口 |
| 新增         | packages/video-schema、services/agent、services/render-worker、remotion-compositor | 这些属于我们自己的创新与工程能力                 |
| 保留人工模式 | src/ui/\* 作为可视化预览/干预工具                                                  | 出现 AI 规划偏差时可人工编辑，而非只能整片重做   |
| 后置         | 多 Agent 分工优化、自动录屏、平板电脑模型扩展、直接 @remotion/three 重构           | 先确保首版能输出一条稳定完整的 MP4               |

## 3.1 不建议一开始做的改动

- 不要立刻把 src/scene 全部迁移到 Remotion 的 React 树：原项目的 useFrame、HTMLVideoElement、OffscreenCanvas 和浏览器 WebCodecs 依赖，迁移后容易产生黑屏与时间不一致。

- 不要拆成十几个微服务、上 Kubernetes 或复杂审批工作流；本地任务队列与一个渲染 worker 即可。

- 不要先建设“全自动代码理解 → 自动录屏”的大工程，再验证基础视频链路。

## 3.2 建议目录组织（增量方式）


```text
device-mockup-studio-main/ # 原仓库先不大规模移动
src/ # 既有 3D 编辑器与渲染模块
automation/ # 新增：稳定工具桥接入口
public/devices/ # 现有真实 GLB
docs/
packages/video-schema/ # 新增：Video DSL + 校验
services/agent-orchestrator/# 新增：AI 编排/工具调用
services/render-worker/ # 新增：无头浏览器驱动/导出
remotion-compositor/ # 新增：全片合成
tests/e2e/ # 新增：金样例与端到端冒烟
```


目录仅为建议，P1 阶段先用少量文件建立 API，不要为了这棵目录树提前重构所有源文件。

# 04｜统一数据协议：Video DSL v0.1

Agent 产出“是什么镜头”，而不是直接生成任意 Three.js 代码。Video DSL 是人类可审查、机器可校验且可版本化的中间协议。设备模型表、动画预设与拍摄参数由确定性工具读取。

## 4.1 建议最小字段

| **字段**                 | **含义 / 约束**                                                         |
|--------------------------|-------------------------------------------------------------------------|
| schemaVersion            | 版本号，例如 0.1.0；解析器按版本迁移                                    |
| canvas                   | width、height、fps，首版建议 1080×1920 / 1920×1080 与 30fps             |
| assets                   | 资产 ID、相对路径、类型（video/image/audio）；禁止无限制绝对网络 URL    |
| shots\[\]                | shotId、deviceId、screenAssetId、durationFrames、模板、动画、背景、镜头 |
| overlays\[\] / audio\[\] | 由 Remotion 处理的字幕、标题、音乐与旁白时间范围                        |
| projectPolicy            | 允许回退、渲染质量、是否启用 Critic 与预算上限                          |

## 4.2 可以由 Agent 实际生成的示例


```json
{
"schemaVersion": "0.1.0",
"canvas": {"width": 1080, "height": 1920, "fps": 30},
"assets": [{"id": "screen-01", "kind": "video", "uri": "assets/demo.mp4"}],
"shots": [{
"shotId": "hero-01", "deviceId": "pixel-9-pro-xl",
"screenAssetId": "screen-01", "durationFrames": 150,
"template": "hero-tilt", "motion": "hero-reveal",
"screenFit": "contain", "screenOffsetFrames": 0
}],
"overlays": [{"startFrame": 0, "durationFrames": 90,
"text": "为效率而生", "kind": "title"}]
}
```


## 4.3 强校验与软约束必须分开

| **硬规则（立即拒绝）**                                    | **软规则（Agent 可自由调整）**       |
|-----------------------------------------------------------|--------------------------------------|
| 缺失资产、未知设备 ID、帧数 \<= 0、无法识别文件、渲染失败 | 镜头是否有冲击力、字幕文案、构图美感 |
| 音视频超出有效时长、未经授权的资产、越权文件路径          | 镜头时长偏好、配色、节奏、讲述顺序   |
| 导出为空文件、关键帧数值 NaN、需要网络却设置完全离线      | 创意探索、反复尝试不同转场           |

建议用 Zod 或 JSON Schema 校验外部 DSL；把 DSL 编译成原仓库 Project/schema 的摄像机与设备 TrackSet。不要直接把当前 Zustand store 作为 Agent 的输出协议。

# 05｜工具接口：让 Agent 真正能操控底层

| **工具名**         | **输入**                   | **产出 / 失败语义**                        |
|--------------------|----------------------------|--------------------------------------------|
| list_devices       | 无 / 可选类别              | 返回模型、资产状态、screenAspect、可用模板 |
| probe_media        | 本地资产 ID/路径           | 时长、分辨率、编码、能否解码               |
| create_device_shot | Video DSL shot             | 生成项目镜头结构与编译摘要                 |
| preview_frame      | shotId、frameIndex         | 预览 PNG + 告警（无模型/屏幕黑帧）         |
| render_device_shot | shotId、输出档位           | 设备镜头 MP4 或 PNG 序列 + manifest        |
| compose_video      | shot manifests、字幕、音轨 | 最终 MP4、字幕文件、工程配置               |
| inspect_render     | 渲染文件、抽样策略         | 技术检验 + 关键帧截图 + 风险提示           |

## 5.1 渲染任务状态机


```text
PENDING → VALIDATING → LOADING → RENDERING → ENCODING → DONE
↘ ERROR（可重试、带错误码）
每个任务保存：jobId / inputHash / startTime / endTime / log / outputManifest
```


## 5.2 关键的工程细节

- Windows 本机可先使用 Playwright 驱动 Chromium 打开本地 Vite/构建页面，注入工程与素材并调用稳定的渲染桥接 API；不能依赖开发用 window.\_\_mockup 作为长期产品 API。

- 导出前需要等模型、环境贴图和录屏首帧 ready；否则 UI 看似成功但成品可能黑屏。

- 优先走已有 WebCodecs MP4；不支持则退回 PNG 序列 + FFmpeg；任何回退必须记录在任务报告。

- 长任务支持取消、超时、失败重试与任务目录隔离；先保证可靠后再优化并发与速度。

- 不在 Agent 产物中直接信任 file://、任意用户输入的 JS 代码或网络资源 URL。

# 06｜Agent 设计：先少角色，逐步演化

建议最小可用架构只有 3 个职责：Planner/Director、Executor、Reviewer。可以在初期由同一个模型分角色调用工具，不必强制搭建三个长期运行的独立进程。

| **角色**                       | **职责**                                                      | **输出 / 不负责什么**                    |
|--------------------------------|---------------------------------------------------------------|------------------------------------------|
| Planner / Director             | 阅读用户 Brief 与功能说明；提炼卖点、节奏、镜头意图；生成 DSL | 输出结构化分镜；不写底层 Three.js 代码   |
| Executor / Tool Agent          | 调用素材分析、创建镜头、预览、渲染、Remotion 合成等确定性工具 | 输出日志与文件；不自行改 DSL 规范        |
| Reviewer / Critic              | 检查缺帧、音画错位、字幕越界、设备遮挡与节奏；提出修订方案    | 出问题时定点重做镜头；不每次强制无限循环 |
| Code Understanding Agent（V2） | 读取 React/Vue/Flutter 源码，理解页面结构、功能与可录屏路径   | 首版不接触用户工程环境与自动执行         |
| Recorder Agent（V2）           | 在隔离环境里启动受支持项目并录制指定功能路径                  | 需额外安全策略和人工授权                 |

## 6.1 控制循环


```text
Plan → Validate → Preview(抽样) → Render → Inspect
↑ │
└── 有问题则局部修订 ←─────┘
达到质量门槛或重试上限 → 输出 + 标记剩余问题
```


避免 StepFlow 早期“过度严谨导致模型兜圈”的问题：每个镜头最多自动重试 2 次作为起始默认值，可配置；视觉建议优先打分提示，不做阻断；只有硬错误阻断交付。

# 07｜分阶段工作安排与验收标准

工期为单人开发、已具备 Node/TS/React/Three.js 基础、能正常安装依赖时的粗略估算。任务可交叉推进；以验收条件而不是日历天数判断完成。

| **阶段**         | **工作重点**                                                         | **预估**  | **阶段交付 / Exit Gate**                               |
|------------------|----------------------------------------------------------------------|-----------|--------------------------------------------------------|
| P0 基线验收      | 原项目启动、20 个测试文件对应的测试/构建/静态检查、4 台 GLB 逐台渲染 | 1–3 天    | 本地可预览；5 秒 1080p 导出；无黑屏/空片；记录机器环境 |
| P1 无头单镜头    | 打通自动加载素材→设备→动画→导出；创建 render-worker/bridge           | 4–7 天    | 单条命令生成 5–10 秒手机旋转 MP4；失败日志清晰         |
| P2 DSL 与工具    | 定义 schema、shot 编译器、工具调用、任务状态/manifest                | 3–5 天    | 无需编辑器手工操作，输入 JSON 能重复输出镜头           |
| P3 Agent 规划    | Brief→分镜→工具执行；先 Planner+Executor，人工可修改                 | 5–8 天    | 输入一句需求及录屏，自动制作 3 镜头粗片                |
| P4 Remotion 合成 | 字幕/配乐/旁白接口/转场/尾版；整片 15–30 秒                          | 4–7 天    | 输出包含片头、设备镜头、字幕、音乐的标准 MP4           |
| P5 评价与稳定性  | 抽帧 QA、黑屏检查、缓存、断点续跑与回归测试                          | 3–6 天    | 固定样例稳定导出，异常可定位并局部重试                 |
| V2 源码理解/录屏 | 受支持框架识别、页面抓取、自动录屏、权限隔离                         | 10–20+ 天 | 受支持的一个 Web 工程可半自动抽取功能并录屏            |

## 7.1 P0：真实基线（最高优先级）

1. 运行 npm ci、npm test、npm run build、npm run lint；记录 Node/Chrome/GPU 版本和失败原因。

2. 以 iPhone 17 Pro / Pixel 9 Pro XL / Galaxy S26 Ultra 分别测试静态截图与 MP4 录屏贴图。

3. 实测正面、侧面、背面、旋转、暂停 Seek、录屏末帧、9:16/16:9、低/高质量导出。

4. 抽取第 0 / 中间 / 最末帧，对比预览与导出，建立截图金样例。

5. 离线测试：只允许使用已打包本地资源；标注 HDRI 外部依赖、Draco 解码器或其他潜在网络加载。

P0 失败时不得推进“Agent 自动出大片”；先修当前仓库在目标 Windows 机器上的环境与渲染问题。

## 7.2 P1：第一个真正的端到端演示

验收演示：提供 demo.mp4 + 指令「用 Galaxy S26 Ultra 做 6 秒慢速旋转展示」→ 自动生成 hero.mp4；视频长度、屏幕内容、设备方向正确；无需手动拖入编辑器。

## 7.3 P2：让模型可控而不是让模型随意写代码

DSL 有版本号、规范化素材引用、合法镜头参数与错误码；输出相同输入与同一工具版本时，相同帧应在容许的编码差异内保持一致。

## 7.4 P3/P4：用户能够直接看到完整宣传片

成功标准：上传录屏 + 写产品卖点 → Agent 给出可修改 3–5 镜头故事板 → 依次生成设备镜头 → Remotion 合成并输出完整 MP4；某一镜头失败允许重渲，不重跑全部。

# 08｜Remotion 集成方案：两条路径与选型

| **方案**                                    | **优点**                                          | **代价/风险**                                                    | **建议**         |
|---------------------------------------------|---------------------------------------------------|------------------------------------------------------------------|------------------|
| A. 浏览器输出设备镜头 → Remotion 合成       | 最大程度保留当前仓库；错误范围小；可单独预览/缓存 | 镜头边界需要统一 fps/时长；中间资产占空间                        | MVP 推荐         |
| B. 直接将 R3F 镜头放入 Remotion ThreeCanvas | 单一时间轴，减少中间编码/转码                     | WebGL headless、视频纹理、useFrame 与 Remotion hook 语义适配复杂 | P5 后专项 PoC    |
| C. 只用原仓库 WebCodecs 做整片              | 短期省掉合成器                                    | 复杂字幕/多音轨/文字排版/转场不便；偏离 Remotion 目标            | 不推荐为长期主线 |

## 8.1 统一时间轴的技术约束

- 所有镜头以整数 frameIndex 与统一 fps 计算时刻，禁止一部分用自由播放的 video.currentTime、一部分用时间轴累积 delta。

- 镜头长度以帧数为权威；原引擎按 t = frameIndex / fps 渲染；Remotion 拼接使用同一个 frame count。

- 旁白、音乐、字幕、过渡层由 Remotion 统一控制；DeviceShot 不负责这些画面包装元素。

- 资产要有 hash / cacheKey：改字幕不应重新渲染 GLB，改相机角度才重新渲染对应镜头。

## 8.2 首版推荐一条中间产物链


```text
input/brief.json + input/demo.mp4
↓
work/storyboard.json（可编辑）
↓
work/shot-001.mp4、shot-002.mp4、shot-003.mp4
↓
work/film.remotion.json（字幕与声音轨）
↓
output/final.mp4 + output/render-report.json
```

# 12｜验收定义与下一轮决策

## 12.1 MVP 完成的客观标准

1. 提供一段录屏 + 简要产品文案，不修改源码即可生成结构化故事板。

2. AI 能调用至少 3 个稳定工具：探测素材、创建镜头、导出镜头；全部生成可追踪任务日志。

3. 至少 2 台内置真实手机 GLB 可以正确贴图并转动；正面不会出现明显黑屏或倒置。

4. 能够输出一条 15–30 秒、至少 3 个镜头的 MP4，含字幕和音乐；可正常播放。

5. 当某一镜头故障，系统返回明确原因或可用回退方案，不以空白视频假装成功。

6. 人工可以改分镜参数并仅重渲受影响镜头，不必整个项目重做。

## 12.2 下一轮必须回答的工程问题

- Windows 目标机器的 GPU、Chrome 与 WebCodecs 能否稳定完成高质量导出？

- 已有录屏同步机制在 30fps 批量导出和视频边界处表现如何？

- 第一版采用 MP4 中间片段还是 PNG 序列以确保关键帧准确度？需用质量/时长测试选型。

- Agent 是否只需调用 DSL 编译器？哪些镜头参数应开放为自由创作变量？

- 用户的典型宣传片更偏 APP 竖屏介绍还是 SaaS 横屏桌面展示？决定下一批模型扩展次序。
